# S4-1：数字员工框架 + 首批三个角色

> 依据：`docs/mcp-ai-orchestration-plan.md` §5.5、§6（S4）。分支 `feat/ai-agents-s4`，基于 main 96f82fc6（S3-2 合并后）。
>
> S4 拆为两个 PR：
> - **S4-1（本批）**：AgentProfile 框架、管理端启停、审计、配额与超额降级，加上三个首批角色。
> - **S4-2**：RAG 自动入库，以及可选的 MCP / 插件转工具。

## 0. 已确认的决定

| 问题 | 决定 |
|---|---|
| 首批角色 | 三个都做：个人秘书、排班管理员、合规专员 |
| 拆分 | 两个 PR（见上） |
| 送达渠道 | 站内通知，加上智能助手里的确认卡：需要确认的动作，点通知进入助手，用 S3 的确认卡确认或取消 |

原则（§5.5）：
- 数字员工只能「发起 + 请求确认」，不会替人直接改数据。
- 每个动作都记录审计。
- 每个角色可以单独启停，单独设置配额；超额后降级，不会停摆。

## 1. 现状

- **晨报**：工作日 08:30 的 beat 任务 `send_daily_digests`，给 `is_active and is_staff` 的用户各派发一个子任务。每个子任务都完整跑一遍编排链路，也就是每人一次 LLM 调用，再写一条 `system` 通知（按日期去重）。
- **合规**：`check_compliance_due_dates` 每天把逾期问题升级为「紧急」，并通知项目负责人；只提醒，没有整改建议。
- **排班**：`Schedule`（值班人员、值班领导），换班申请走 `swap_service.create_swap_by_query`（申请人本人发起）。没有任何冲突巡检。
- **审计**：`AgentEvent` 必须挂在 `AgentTask` 下。如果把数字员工的巡检当成 AgentTask，这些任务会出现在用户的「多 Agent 任务」面板里，因此需要单独的审计表（见 §2）。
- **确认**：S3 的确认草稿存在缓存里，只有 10 分钟有效期，不适合「今天巡检、明天才点开通知」的场景，需要一个持久化的「待确认事项」。

## 2. 模型（`smart_assistant` 迁移 1 个）

- **`AgentProfile`**：
  - 基本信息：`key`（唯一：secretary / scheduler / compliance）、名称、职责说明、系统提示词、工具集白名单（JSON）、数据范围说明。
  - 触发：触发方式（被动 / 定时 / 业务事件）、定时说明（仅展示）。
  - 管理：启停开关、负责人（可空）、每日 LLM 配额、每日动作配额。
- **`AgentRun`**：一次运行。记录角色、触发方式（beat / manual）、状态（running / succeeded / degraded / failed / skipped）、起止时间、统计（JSON）、错误摘要。
- **`AgentRunEvent`**：审计事件。字段：运行、事件类型、相关用户、payload（JSON，不存正文）、时间。事件类型：
  - `run.started` / `run.completed` / `run.failed` / `run.skipped`
  - `llm.call` / `llm.fallback`
  - `notify.sent`
  - `proposal.created` / `proposal.approved` / `proposal.rejected` / `proposal.expired` / `proposal.failed`
  - `quota.exceeded`
  - `config.changed`（管理端修改启停、配额、负责人）
- **`AgentProposal`**：发给某个用户的待确认事项。
  - 字段：角色、运行、用户、类型（kind）、fields、preview（与 S3 预览结构相同）、状态（pending / approved / rejected / expired / failed）、`expires_at`、决定时间、结果、去重键。
  - 同一用户、同一去重键同时只允许存在一条 pending（条件唯一约束），巡检每天重跑也不会重复打扰。
- **数据迁移**：创建三个角色。个人秘书**默认开启**（接替现有晨报，保持原来的推送）；排班管理员、合规专员**默认关闭**（新的主动行为，由管理员在管理端开启）。
- **配额计数**：按当天的 `AgentRunEvent` 统计，不另建计数表，审计和计数同源。

## 3. 运行框架（`smart_assistant/staff/`）

- `RoleRunner` 基类，加上注册表（key → runner）。
- `RunContext` 提供三个受配额约束的动作，每个动作都写审计：
  - **`notify(user, title, content, link, dedupe_key)`**：写站内通知。
  - **`propose(user, kind, fields, preview, dedupe_key, expires_at)`**：创建 `AgentProposal`，再发一条通知，链接为 `/smart-assistant?proposal=<id>`。
  - **`llm(prompt)`**：调用 LLM。配额用完或调用失败时返回 None，并记录 `llm.fallback`，角色改用模板内容，也就是**降级**。
- **动作配额用完**：后续动作全部跳过并记录 `quota.exceeded`（每次运行只记一次），运行状态为 degraded；如果角色设置了负责人，给负责人发一条提示。
- **Celery 任务 `run_agent_profile(key, trigger)`**：
  - 角色关闭时写一条 skipped 运行后返回。
  - 同一角色已有 running 的运行时跳过（防止并发重复）。
  - 异常记录为 failed，不向 Celery 抛出。
- **beat**：
  - 保留 `smart-assistant-daily-digest`（任务名不变，数据库调度器里已有这条），改为触发 secretary。
  - 新增 `agent-scheduler-patrol`（工作日 16:00）和 `agent-compliance-patrol`（工作日 09:10）。

## 4. 三个角色

### 4.1 个人秘书（secretary）

- **目标用户**：与原晨报相同（`is_active and is_staff`），推送范围不变。
- **晨报内容改为直接从数据库汇总**，不再每人调用一次 LLM：
  - 今日备忘：今天到期、未完成的备忘录。
  - 值班：今天和明天我担任值班人员或值班领导。
  - 会议：今天我的会议室预约。
  - 待我处理的换班：我是接收方、待我同意的申请。
- **LLM**：只用来为每人生成一句「今日提示」，在配额内调用，超额就省略。默认配额为 0，即不调用 LLM；管理员调高后生效。原 `digest.py` 删除。
- **通知**：标题和去重键沿用原晨报，切换当天不会重复推送。链接为 `/smart-assistant`。
- 保留 `send_single_digest` 任务名，改为调用秘书角色给单个用户生成晨报，兼容已经在队列里的任务。

### 4.2 排班管理员（scheduler）

巡检今天起 7 天内的排班，发现以下三类问题：

| 问题 | 处理 |
|---|---|
| 值班人员当天是「计划中 / 进行中」试验的责任人（试验时段与值班日重叠） | 给值班人员（需关联了账号）创建待确认事项「发起换班申请」，并推荐一位接替人，见下 |
| 值班人员或值班领导已离职 | 通知负责人；没有设置负责人时，通知管理员 / HR |
| 同一人同日既是值班人员又是值班领导 | 同上 |

- **推荐接替人**：
  - 条件：在职且关联了账号，不是本人，值班日前后 1 天都没有值班，当天不是任何试验的责任人。
  - 排序：优先未来 30 天值班次数最少的人。
  - 找不到合适的人时，只通知值班人员，不创建待确认事项。
- **确认后**：以值班人员本人身份发起换班申请，之后走正常的换班流程（接收方同意、生效）。
  - 新增 `swap_service.create_swap_for_personnel`，直接使用人员和排班对象，不按姓名查找，避免重名时取错人。
- 这个动作不可撤销：换班申请有自己的撤销流程。确认卡上会注明。
- **执行前重新校验**：排班仍然属于该用户、日期还没过、没有进行中的同日换班申请。
- **有效期**：48 小时，并且不晚于值班日当天 00:00。

### 4.3 合规专员（compliance）

- **范围**：状态为「待处理 / 处理中 / 紧急」，且 3 天内到期或已逾期的合规问题。
- **汇总通知**：每位项目负责人每天收到一条，列出本人名下的这些问题，按天去重。这和逾期升级通知不重复：那一条是单条问题的紧急提醒。
- **整改建议草稿**：对「逾期或紧急」且当天还没有待确认建议的问题，调用 LLM 生成整改建议，最多 5 条，每条不超过 300 字。
  - LLM 配额用完或调用失败时，按问题类型改用模板清单（降级）。
- **待确认事项**：给项目负责人创建「保存整改建议」。
  - 确认后为负责人创建一条备忘录：标题「整改：项目 · 问题摘要」，正文为建议内容，提醒时间取到期日 09:00（已过期则不设提醒）。
  - 写入 `AgentWriteLog`，可用备忘录的撤销流程撤销。

## 5. 待确认事项接口

| 接口 | 说明 |
|---|---|
| `GET /api/smart-assistant/proposals/?status=pending` | 本人的待确认事项 |
| `GET /api/smart-assistant/proposals/<id>/` | 本人的一条；他人的返回 404 |
| `POST .../proposals/<id>/approve/` | 确认执行，见下 |
| `POST .../proposals/<id>/reject/` | 取消；非 pending 时返回 409 |

- **approve** 的处理：
  - 在行锁内检查状态：非 pending 返回 409；已过期返回 410，并把状态置为 expired。
  - 执行对应类型的处理器，在事务内完成。
  - 返回格式与 S3 确认接口一致：`answer`、`confirmed`、`write_log_id`、`reversible`。
  - 业务冲突（例如排班已变化）返回 409，状态置为 failed。
- 每次确认、取消、过期、失败都写 `AgentRunEvent`。
- 定期清理：beat 每小时把过期的 pending 置为 expired。

## 6. 管理端

**接口**（仅管理员）：

| 接口 | 说明 |
|---|---|
| `GET /api/smart-assistant/agent-profiles/` | 角色列表：配置、当天用量、最近一次运行 |
| `PATCH .../agent-profiles/<key>/` | 只允许改 `enabled`、`daily_llm_quota`、`daily_action_quota`、`owner` |
| `POST .../agent-profiles/<key>/run/` | 立即运行一次（Celery 异步）；角色关闭时返回 409 |
| `GET .../agent-profiles/<key>/runs/` | 最近 20 次运行，每次附带事件 |

**前端**：「AI 管理 → 数字员工」页（`/control-panel/ai/staff`）。
- 表格列：名称、职责、定时、启停开关、配额（可编辑）、今日用量、最近运行。
- 操作：「立即运行」；展开可查看最近运行和事件。

## 7. 前端（确认渠道）

- 智能助手页读取 `?proposal=<id>`（`ProposalLinkWatcher`，仅在 Router 内渲染）：拉取该事项，在消息列表里插入确认卡，然后去掉地址参数。
- 确认卡显示「来自数字员工：<角色名>」。
- `WriteConfirmCard` 支持传入自定义的确认 / 取消函数。待确认事项调用 proposals 接口；已处理或已过期时显示对应状态。

## 8. 测试

- **框架**：
  - 关闭的角色会被跳过；同一角色不会并发运行；异常记录为 failed。
  - 动作配额用完后跳过后续动作并记录 `quota.exceeded`；LLM 配额用完后降级为模板。
  - 同一去重键不会重复创建待确认事项；审计事件齐全。
- **三个角色**：
  - 晨报各段内容，去重键与原晨报一致。
  - 冲突识别准确（试验冲突、离职、同人兼任）；推荐接替人时正确排除；确认后换班申请创建成功；执行前排班已变化返回 409。
  - 合规汇总按负责人分组；建议生成有降级；确认后生成备忘录，并可撤销。
- **接口**：他人的事项返回 404，已处理的 409，已过期的 410；管理端只有管理员能用，PATCH 只能改允许的字段。
- **前端**：数字员工页；智能助手页通过 `?proposal=` 打开确认卡。

## 9. 不做（S4-2 或以后）

- RAG 自动入库、MCP / 插件转工具（S4-2）。
- 业务事件触发（本批只做定时和手动）。
- 在管理端编辑定时规则或提示词（本批只读展示）。
- 用户自己订阅或退订晨报。
