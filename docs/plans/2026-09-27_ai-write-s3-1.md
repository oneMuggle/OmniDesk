# S3-1：AI 写操作统一流程 + 首批三类写能力

> 依据：`docs/mcp-ai-orchestration-plan.md` §5.3、§6（S3）。分支 `feat/ai-write-s3-1`，基于 main 08e99fd（S2-2 合并后）。
>
> S3 拆为两批：
> - **S3-1（本批）**：统一的「草稿 → 确认 → 执行 → 可撤销」流程，加上通知标记已读、会议室预约和取消、合规问题状态更新。
> - **S3-2**：公告草稿（公告模型新增「草稿」状态）和试验日程（Trial）创建。

## 1. 现状与缺口

已有：
- confirm-replay：写工具先 dry_run 生成草稿，草稿存入短期缓存（10 分钟），用户凭一次性 token 确认后执行。跨用户重放返回 403，重复使用返回 409，执行前按当前用户重新授权。
- `AgentWriteLog`：记录 before / after，`POST write-logs/{id}/revert/` 可回滚。
- 备忘录的增、改、删是现成的参考实现（按 `updated_at` 做版本校验，确认时加行锁）。

缺口：

| # | 缺口 | 影响 |
|---|---|---|
| G1 | 确认卡片只显示「请确认工具操作」，没有目标对象、字段变化、影响范围、权限来源 | 不满足 §5.3 的卡片要求；用户不知道自己在确认什么 |
| G2 | 智能助手页确认后，只有文件下载会显示结果，其他写操作没有任何反馈；按钮文字写死为「确认生成」 | 写完不知道成没成功 |
| G3 | AI 抽屉完全不处理确认事件 | 在抽屉里发起写操作会没有反应 |
| G4 | 没有「取消」动作，草稿只能等过期 | 拒绝不可追溯 |
| G5 | 撤销接口写死只支持备忘录；前端没有撤销入口 | 新写能力无法回滚 |
| G6 | `memo_delete`（删除）当前默认可用 | 违反「删除默认关闭」 |

## 2. 统一流程（后端）

### 2.1 确认预览（解决 G1）

写工具的 dry_run 结果新增 `draft.preview`，**只能由服务端根据数据库记录生成**，不能拼接用户原话：

```json
{
  "action": "预约会议室",
  "target": {"type": "会议室预约", "label": "3 楼大会议室 · 10-08 14:00–15:00"},
  "changes": [{"field": "status", "label": "状态", "before": "待处理", "after": "已解决"}],
  "affected_count": 1,
  "affected_label": "条预约",
  "permission_source": "本人预约",
  "reversible": true,
  "risk": "write"
}
```

- `public_confirmation_draft` 只公开白名单字段：字符串截断到 120 字、changes 最多 10 项、items 预览最多 5 条。卡片摘要由 preview 生成（例如「将预约 3 楼大会议室 10-08 14:00–15:00」）。
- 没有 preview 的旧工具保持原样，不受影响。

### 2.2 独立的确认 / 取消接口（解决 G4，也服务 G2、G3）

- `POST /api/smart-assistant/confirmations/{token}/approve/`：沿用现有 replay 的全部校验（过期 410、跨用户 403、已使用 409、执行前重新授权）。
  - 返回 `answer`、`write_log_id`、`reversible`、`preview`。
  - 工具返回冲突类错误（`stale_confirmation`、`booking_conflict`、`state_conflict`）时返回 **409**，其他业务失败返回 400。
- `POST /api/smart-assistant/confirmations/{token}/reject/`：消费掉 token，之后不能再确认，并记一条结构化日志。重复取消返回 409，已过期返回 410。
- 保留旧的 `chat` 接口带 `confirm_token` 的方式，兼容已有客户端。
- 只有点击确认卡片（凭 token）才会执行。在对话里输入「确认」「同意」只是普通消息（会写测试证明）。

### 2.3 通用撤销（解决 G5）

新建 `smart_assistant/writes/` 包：
- `preview.py`：生成预览，并做公开字段过滤。
- `write_log.py`：`record_write(...)` 统一写 `AgentWriteLog`（关联任务、会话）。
- `revert.py`：按目标模型注册的撤销处理器 `register_revert_handler("app.Model", handler)`。
  - handler 负责三件事：定位目标并加行锁、校验当前值、执行撤销；当前值变化时抛 `RevertConflict` → 409。
  - 备忘录逻辑原样迁入 handler，行为不变（包括「删除不可回滚」）。
- `write-logs/{id}/revert/` 改为按 `target_model` 分发给对应 handler；未注册的模型返回 409。撤销时会重新校验权限（例如已不再是项目负责人就不能撤销）。

### 2.4 删除默认关闭（解决 G6）

- 新增开关 `SMART_ASSISTANT_ENABLE_DESTRUCTIVE_TOOLS`，默认 `False`；`memo_delete` 挂在这个开关上。
- 能力注册自检新增一条规则：`risk_level="destructive"` 的工具必须声明 `feature_flag`。
- **行为变化**：AI 删除备忘录默认不可用；页面上的手动删除不受影响。

## 3. 三类写能力

所有新工具都满足以下约定：
- `require_confirmation=True`，并声明 `ConfirmPolicy.USER`。
- dry_run 只读数据库，生成 preview；确认阶段在事务中加行锁，校验版本或状态，再执行，并写 `AgentWriteLog`。
- 参数优先使用原生函数调用给出的结构化参数；走意图分类路径时，由提取器从原话中解析。
- 权限与对应页面接口一致，AI 不会拥有比页面更大的权限。

| 工具 | 范围与权限 | 冲突 / 幂等 | 撤销 |
|---|---|---|---|
| `notification_mark_read` 通知标记已读 | 只能处理本人的通知；可指定单条、按关键词或全部未读，单次最多 50 条 | 确认时已读的会跳过，结果中报告实际处理条数 | 恢复为未读（只恢复本次标记、且之后没被再次处理的那些） |
| `meeting_room_book` 预约会议室 | 所有登录用户（与页面一致）；会议室按名称唯一匹配 | 确认时锁住会议室行，再走模型自带的冲突检查（已有预约、维护时段、开始时间不能早于现在）；冲突返回 409 | 删除本次创建的预约（前提是创建后没被修改） |
| `meeting_room_cancel` 取消会议室预约 | **只能取消本人**、未开始的预约；即使是管理员，AI 也不能取消别人的预约 | 按 `updated_at` 做版本校验 | 如果原时段仍然空闲且未开始，就重建预约（新 id），否则返回 409 |
| `compliance_issue_update_status` 更新合规问题状态 | 与页面一致：管理员或项目负责人（`ComplianceChecker.can_modify_issue`）；卡片显示权限来源 | 按 `updated_at` 做版本校验；状态必须是合法值且与当前不同 | 当前状态仍等于本次设置的值时，恢复为原状态；撤销时再次校验权限 |

## 4. 前端

- 新增 `WriteConfirmCard` 组件，智能助手页和 AI 抽屉共用，替换原来的 `Modal.confirm`（解决 G2、G3）。
  - 卡片内容：操作名称、目标对象、字段变化表（原值 → 新值）、影响条数、权限来源、是否可撤销。
  - 卡片按钮：「确认执行」和「取消」。
  - 执行后显示结果；可撤销时显示「撤销」按钮，调用 `write-logs/{id}/revert/`。
  - 409、410 等错误在卡片内提示，比如「预约时段已被占用」「确认已过期，请重新发起」。
- 文件生成类（office）确认后仍显示下载卡片，行为不变。

## 5. 测试

每个新写工具都覆盖：**批准、拒绝、重复提交（token 已用 409）、取消后再确认、撤销、撤销冲突 409、执行时冲突 409、越权**。另外测试：
- 在对话中输入「确认」不会执行写操作。
- 删除类工具在开关关闭时不可见、不可执行。
- 撤销接口：未注册的模型返回 409；非本人的写日志返回 404。
- 公开预览：字段白名单与长度截断；不包含用户原话。
- 前端：确认卡片的各种状态（待确认、执行中、成功、已撤销、已取消、出错）；抽屉内能完成确认。

## 6. 不做（留到 S3-2 或以后）

- 公告草稿、试验日程创建：放在 S3-2。
- 双人审批：本批所有写操作都是单人确认（按你第四轮的决定）。
- 多 Agent 任务里写步骤的确认 UI：沿用现有机制，本批不改。
- 修改会议室预约（改时间或主题）：需要时再加。

## 8. 实施记录（与方案的差异和补充）

- **重复提交的提示**：token 被消费后，草稿本身就删掉了，重复点会被当成“过期”（410）。为了让用户看得明白，消费时另存一个短期标记（有效期同草稿）：本人再点「确认」或「取消」返回 409，code 为 `confirmation_already_used` 或 `confirmation_already_rejected`；其他人一律返回 410，不暴露结果。
- **时间比较统一转 UTC**：预约快照、通知 `read_at` 在写日志和撤销校验时都先转 UTC 再序列化。原因是内存对象带本地时区，数据库读回是 UTC，直接比字符串会误判为“已被修改”。
- **前端确认卡**：`WriteConfirmCard` 自己调用确认、取消、撤销三个接口，聊天页和抽屉只负责把 confirmation 事件转成一条卡片消息。原来的确认弹窗和“重发一次聊天请求”的做法已删除：旧做法重发时用的问题文本已被清空，而且只处理文档下载结果。文档生成的下载卡片现在显示在确认卡里。
- **请求没发到服务端时**（例如断网）允许再点一次确认；服务端已经处理过的 token 不能重试，卡片会显示原因。
- **测试**：后端新增 `test_s3_write_tools.py`（34 个）、`test_s3_write_flow.py`（24 个）；前端新增 `WriteConfirmCard`、`QuickAssistant.confirm`、`SmartChatPage.confirm` 三个测试文件。
