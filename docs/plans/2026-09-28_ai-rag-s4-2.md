# S4-2：知识自动入库（公告 + 文档库），检索按原始权限过滤

> 依据：`docs/mcp-ai-orchestration-plan.md` 的 G7（知识来源断裂）、§5（知识管道）、§6（S4）。
> 分支 `feat/ai-agents-s4-2`，基于 main d24a295b（S4-1 合并后）。

## 0. 已确认的决定

| 问题 | 决定 |
|---|---|
| 首批入库来源 | 已发布的公告 + 文档库（Paperless）里的文档 |
| 权限 | 入库时记下每个 RAGFlow 文档对应的本系统对象；检索结果回到本系统后，逐条按用户能否看到原对象过滤 |
| MCP / 插件转工具 | 本批不做，以后单独开批次 |

## 1. 现状

- 只有智能助手里手动上传的文档（`KnowledgeBaseDocument`）会进 RAGFlow，入口是 `knowledge_base.py` 的 `perform_create`。
- 公告和文档库的内容不会进 RAGFlow。
- `knowledge_qa` 工具经 `RAGRouter.search_multi` 检索，**不区分用户**。现有知识库被视为公共知识。
- 工具结果缓存已按用户隔离（`tool:scoped:v2`），过滤后的结果不会串给别人。
- `ragflow_service` 的 `query` 接口直连 RAGFlow 聊天助手，绕过本系统。但只有管理员能 POST，本批不改；部署说明要求**不要把自动入库的数据集挂到 RAGFlow 聊天助手上**。
- 可见规则：
  - **公告**：已发布的所有登录用户可见；草稿只有管理员和 HR 可见。
  - **文档库**：staff 看全部，其他人只看自己上传的（`paperless_proxy.selectors.visible_bindings`）。
- 需要注意的现有行为：
  - 公告「发布」接口用条件 `update()` 防止重复发布，**不会触发 `post_save`**。
  - Paperless 上传是异步的，刚上传时 OCR 文本可能还没有。

## 2. 模型（`smart_assistant` 迁移 1 个）

**`KnowledgeSource`**：一个业务对象对应一条入库记录。

| 字段 | 说明 |
|---|---|
| `source_type` | `announcement` / `paperless_document` |
| `source_id` | 业务对象主键 |
| `ragflow_dataset_id`、`ragflow_document_id` | RAGFlow 里的位置；未入库时为空 |
| `content_hash` | 入库内容的 sha256，内容没变就不重复上传 |
| `status` | `pending`（待入库或等待 OCR）/ `ingested` / `failed` / `removed` |
| `attempts`、`last_error` | 连续失败次数和错误摘要，成功后清零 |
| `ingested_at`、`created_at`、`updated_at` | 时间 |

- `(source_type, source_id)` 唯一；`ragflow_document_id` 建索引，用于检索后反查。

## 3. 入库流程（`smart_assistant/knowledge/`）

**配置**
- 新增 `SMART_ASSISTANT_INGEST_DATASET_ID`（环境变量），并且需要有启用的 `RagflowConfig`。
- 两者缺一时，自动入库**整体关闭**：信号不入队，任务直接返回，管理端显示「未配置」。
- 这个数据集专门给自动入库用，不和手动上传的数据集混用。

**生成入库内容**：每类来源一个函数，返回 `(标题, 正文)`；不该入库时返回 None。
- **公告**：只有已发布的才入库。正文 HTML 转成纯文本，前面加上标题和发布时间。
- **文档库**：只有已同步到 Paperless 的才入库（`paperless_id` 不为空）。用 Paperless 的 OCR 文本（`get_document()["content"]`）。
  - OCR 文本为空时，状态保持 pending，不算失败，下次对账再试。
- 正文最长 200,000 字，超出截断。

**同步一条 `sync_source(source_type, source_id)`**
1. 生成入库内容；为 None 时（对象已删除、公告改回草稿等）删除 RAGFlow 文档，状态置为 removed。
2. 内容 hash 没变且已入库时，跳过。
3. 否则先删旧的 RAGFlow 文档，再上传新的 Markdown 文件（`announcement-<id>.md` / `paperless-<id>.md`），然后触发解析。
4. 失败时状态置为 failed，记下次数和错误摘要（不含正文）；连续失败 5 次后，对账不再自动重试，只能在管理端手动重试。

**触发**
- **公告**：`post_save` / `post_delete` 信号；发布接口在事务提交后显式入队。
- **文档库**：`DocumentBinding` 的 `post_save`（`paperless_id` 已有时）/ `post_delete` 信号。
- 以上都用 `transaction.on_commit` 入队 Celery 任务 `sync_knowledge_source`。
- **对账**：beat `knowledge-ingest-reconcile` 每 30 分钟运行一次，每次最多处理 100 条：
  - 应入库但没有记录，或业务对象比记录新；
  - pending，或失败次数少于 5 次；
  - 已入库但业务对象已删除或不再符合条件。
  - 对账能兜住信号漏掉的情况（例如 `update()`、手工改数据库）。

## 4. 检索时按权限过滤

- `RAGRouter.search_multi` 在已配置时**总是额外检索入库数据集**，并给这些结果打上 `_ingest` 标记。
  - 入库数据集多取一些（top_k × 3），过滤后再截断。
- `knowledge_qa` 工具拿到结果后调用 `filter_chunks(user, chunks)`：
  - 没有 `_ingest` 标记的结果（手动上传的公共知识库）：保持原样。
  - 有标记的结果：按 `document_id` 反查 `KnowledgeSource`，找不到记录、记录不是 ingested，或当前用户看不到原对象，就**丢弃**。
    - **公告**：原对象存在且已发布。
    - **文档库**：`visible_bindings(user)` 里有这条记录。
  - 当前用户识别不出时，入库结果一律丢弃。
- 检查的是**当前**业务数据，因此对象删除、公告改回草稿或文档权限变化时，即使 RAGFlow 里的文档还没删掉，也立即查不到。
- 保留下来的结果在 `sources` 里标明来源，例如「公告：<标题>」「文档库：<标题>」。

## 5. 管理端

**接口**（仅智能助手管理员）：

| 接口 | 说明 |
|---|---|
| `GET /api/smart-assistant/knowledge-sources/summary/` | 是否已配置；按来源、状态统计的数量；最近 20 条失败记录 |
| `POST .../knowledge-sources/reconcile/` | 立即对账（Celery 异步） |
| `POST .../knowledge-sources/<id>/retry/` | 重试一条（清零失败次数后入队） |

**前端**：「AI 管理 → 知识入库」页（`/control-panel/ai/knowledge`）。
- 显示是否已配置、各状态数量、失败列表（来源、标题、错误、次数、重试按钮）。
- 提供「立即对账」按钮。

## 6. 测试

- **入库内容**：
  - 公告：已发布才入库，HTML 转为纯文本；草稿返回 None。
  - 文档库：未同步时返回 None；OCR 为空时保持 pending。
- **同步**：首次上传并解析；内容不变时跳过；内容变化时先删旧文档再上传；对象删除后移除；失败时记录；未配置时整体跳过。
- **触发**：保存、删除、发布接口都会入队；未配置时不入队；对账能覆盖漏掉的对象，并跳过失败 5 次的。
- **检索过滤**：
  - 普通用户看不到别人的文档库内容，staff 能看到；
  - 公告改回草稿或删除后立即查不到；
  - 反查不到记录的入库结果被丢弃；手动上传的知识库结果不受影响；
  - 识别不出用户时，入库结果全部丢弃。
- **管理端**：只有管理员能用；汇总内容正确；重试和对账会入队。
- **前端**：知识入库页的渲染、重试和对账。

## 7. 不做

- 改造 `ragflow_service` 的直连聊天接口。
